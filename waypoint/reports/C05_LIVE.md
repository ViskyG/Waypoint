# C05.4 / C07.2 — целевая проверка действующего Codex

Статус: целевая живая проверка новой реализации и восстановления после перезапуска пройдена в описанном объёме. Два обнаруженных дефекта исправлены и повторно проверены; неудачные промежуточные опыты сохранены отдельно.

Проверяется существующий Codex владельца, без запуска App Server, новых inference turns, управления агентами или изменения глобальных настроек. Выбранный root подтверждён родительским исполнителем через `CODEX_THREAD_ID` и `session_meta.payload.id`. У дочернего исполнителя этой проверки собственный `payload.id`, отдельный от root; родитель и fork подтверждены метаданными.

Проверка окружения, 17 октября 2026:

- Linux; `session_meta.cli_version`: `0.160.1`.
- Установленное расширение VS Code `openai.chatgpt`: `26.930.61225`.
- Существующий Unix socket `$HOME/.codex/ipc/ipc.sock`: настоящий socket, владелец — текущий UID, права `0600`.
- Фактически проверен протокол существующего owner: little-endian 32-bit length + JSON, discovery/follower версии 1. Owner обнаружен без запуска нового App Server.

Подготовлен `tools/verify_live.py`. Он открывает SQLite только `mode=ro`, читает чужие rollout-файлы только по первой строке метаданных и полные события — только у выбранного семейства. Сопоставляет native ID, тип и оригинальный текст завершённых сообщений/действий внутри процесса; выводит только счётчики и равенства. `response_item` без native ID исключён из доказательства точной межисточниковой идентичности. По явному `--ipc-snapshot` выполняет один ограниченный read-only hydration существующего owner, закрывает собственную подписку и сравнивает оригинальное IPC-содержимое с текущей БД. Тела сообщений и снимки в отчёт не записываются.

Метаданные родства и живые IPC activity-события учитываются отдельно. Историческая связь сама по себе не доказывает одновременную работу потомков. Непроверенные естественные жизненные циклы будут названы явно.

Выполненный запуск после готовности нового адаптера и штатного collector:

```bash
python3 waypoint/tools/verify_live.py \
  --database .runtime/data/waypoint.db \
  --rollouts "$HOME/.codex/sessions" \
  --root VERIFIED_OWNER_THREAD_ID \
  --ipc-snapshot "$HOME/.codex/ipc/ipc.sock" \
  --output waypoint/evidence/live-target.json
```

`VERIFIED_OWNER_THREAD_ID` — обозначение места для локально подтверждённого ID, а не допустимое значение команды.

Результаты первого фактического чтения owner IPC:

- Два полученных snapshot, размер последнего frame — 703 978 байт.
- По native ID, типу и оригинальному тексту точно совпали 49 `commandExecution`, 7 `agentMessage`, 1 `userMessage`. Несовпадений в сравниваемых строках нет.
- Отправлены только `initialize`, `thread-owner-discovery`, `thread-follower-load-complete-history`, `thread-stream-following-changed`. Собственная подписка закрыта; команд управления исполнителем не было.
- В БД нет дублирующихся ключей `(project, agent, native item ID)`. Receipt root был committed, `hydrating=false`, revision 8.

Одна последующая проверка на естественном ходе текущей работы, без повторного snapshot:

- 8 выбранных native agents присутствуют в БД, все 7 родительских связей точно совпадают с исходными метаданными.
- С завершёнными rollout items точно совпали 25 `agentMessage` и 9 `userMessage`; несовпадений нет. Все 23 исходных `Reasoning` имели пустые provider-visible `summary_text` и `raw_content`: их отсутствие в UI ожидаемо, скрытый текст не восстанавливался.
- Root receipt достиг revision 55, `hydrating=false`. После установленной интегратором границы seq 236 записаны 27 `item.upsert`, 14 `agent.activity`; оба реально сфокусированных item имеют одновременно несколько узлов и ребро.
- Только root имел подтверждённый отдельный IPC activity record (`running`). Наличие потомков доказано реальными metadata/rollout, а отдельный live IPC owner каждого потомка не подтверждён.

Обнаружены реальные нативные жизненные циклы `task_started`/`task_complete` и `SubAgentActivity` с `kind=completed`, ссылкой на выбранного потомка и `agent_path`. В последнем нет текстового поля. Эти конкретные события стали основанием ограниченного дополнения адаптера; финальная проверка проекции описана ниже. Исторические сообщения источника не выдаются за одновременный live IPC всех детей.

Первое восстановление после перезапуска собственного сервиса/collector не принято: observer получил `idempotency_conflict`, его committed root receipt остановился на revision 155; реальный Codex продолжил работать, независимое read-only чтение owner оставалось доступно. Причина локализована: при повторном использовании source generation сбрасывался ordinal; одинаковый event ID создавался с новым `at`. Защита Store корректно отказала в неодинаковом повторе. История этого неудачного опыта сохранена отдельно в `evidence/live-target-restart-failure.json`, без текстов переписки.

В этом же опыте уже совпали обе исходные `subAgentActivity` из rollout: native ID, тип, `kind`, ссылка на native child, `agent_path`, пустой текст. Самостоятельный live IPC lifecycle всех детей тогда не принят: часть backfill была остановлена указанной ошибкой. Ошибка передана владельцу адаптера для точечного исправления; финальная запись не должна выдавать этот первый перезапуск за успешный.

После исправления первого дефекта восстановление root IPC принято: receipt достиг revision 169, все rollout cursor имеют normalization version 2, оба канала показывают `connected`, все 71 завершённое IPC-действие, 11 сообщений агента и 1 пользовательское сообщение совпали; все 32 `subAgentActivity` сохранили native ID/тип. Непринятых/несовпавших IPC items в этой выборке нет. Сбой `idempotency_conflict` исчез.

При этом сравнением реальных потомков обнаружен второй отдельный дефект: три естественных fork-файла содержат сначала собственный `session_meta`, потом скопированный родительский `session_meta` и prefix истории родителя. Наивное следование последнему meta оставляло собственную деятельность детей у родителя. Этот частичный результат сохранён в `evidence/live-target-fork-attribution-failure.json`. Найден явный безопасный boundary: перед первым собственным turn присутствует `event_msg.thread_settings_applied.thread_id`, точно равный подтверждённому ID ребёнка. Содержимое `thread_settings` не читается для наблюдения. Этот marker позволяет сохранить родительский prefix как родительский и затем вернуться к собственному native executor без временной эвристики. Исправление принято: normalization version 3 сохраняет подтверждённый file executor и отдельный context унаследованной истории.

Три ранее неверно связанные проекции сообщений исправлены интегратором добавочными событиями `item.identity_corrected`: исходный ledger не переписан, порядок первого receipt сохранён, точный retry идемпотентен. Для каждого исходного ключа была отдельно проверена собственная секция после явного marker, исходный record offset/generation/source-location ID, равенство текста локально и отсутствие противоречащего IPC provenance. Санитизированный итог — `evidence/identity-correction.json`; приватный список ключей остаётся вне передачи.

Финальная целевая приёмка после исправлений:

- Actual owner: два snapshot, последний frame 947 704 байта. Точно совпали native ID, тип и оригинальный текст 83 завершённых `commandExecution`, 12 `agentMessage`, 1 `userMessage`. Native ID/тип совпали у всех 36 `subAgentActivity`, 5 `fileChange`, 1 `mcpToolCall`; текст непроанализированных форматов этим утверждением не охвачен. Непринятых/несовпавших IPC items нет. 100 reasoning items без provider-visible текста исключены явно.
- После одного ограниченного followup без нового IPC snapshot завершившаяся во время первого чтения одна message/lifecycle запись догнала БД: 52 `agentMessage` и 15 `userMessage` из rollout точно совпали, все 3 исходных `subAgentActivity` сохранили оригинальные metadata. Pending и несовпадений нет.
- Все 8 выбранных native agents присутствуют, все 7 родительских связей совпали. Все 8 native rollout cursor соответствуют собственному подтверждённому executor. Последнее состояние всех 8 источников согласовано с проекцией: 5 `idle`, 3 `running`. Provenance сохраняет различие исторических rollout observations и текущего root IPC.
- Root receipt прошёл 155 → 169 → 277 → 287, финально `hydrating=false`. Все rollout cursor имеют normalization version 3. Оба канала `connected`, `idempotency_conflict` отсутствует. Дублирующихся native ключей нет.
- Верификатор успешно отправил собственный unfollow и закрыл socket. Отправленные методы входят в прежний read-only allowlist; команд запуска, остановки, resume или approval не было. Codex и действующие агенты продолжили работу при перезапусках наблюдателя.

Задержка от provider emission до браузера не измерялась (`n=0` у независимого верификатора). Интегратор отдельно измерил реальный путь от входа Follower callback до durable HTTP receipt: `n=3`, две hydration и одна естественная incremental запись, median 86,09 мс, max 235,99 мс (`evidence/live-ingest-timing.json`). Это не provider-to-browser latency, SLA или универсальная совместимость других клиентов.

Настоящий браузер и пользовательские переходы проверяет интегратор отдельно. Общие unit/fixture проверки не подменяют эти фактические результаты. Финальная санитизированная запись — `evidence/live-target.json`; два неудачных промежуточных опыта сохранены рядом. Приватные тексты, capability, снимки, список исправляемых native ключей и рабочая SQLite в передачу не входят. Отдельный live IPC owner каждого ребёнка и полный возможный набор событий будущих версий не подтверждены; зашифрованные reasoning не восстанавливаются.
