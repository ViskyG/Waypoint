The existing extension IPC uses a private, undocumented frame protocol observed for openai.chatgpt-26.930.61225-linux-x64. Compatibility is version-specific and must not be promoted to an official stable contract.
P10: Same natural active owner, in-place JSONL tail (no frozen SQLite copy), owner-side IPC snapshot/revision and stream matching by completed item ID + normalized type + terminal status. One valid matched item (n=1): IPC−JSONL first-detection delta +0.529ms, owner API−JSONL +47.421ms, with select step up to 50ms and API roundtrip ~34–46ms. These are observation-clock deltas, NOT delivery-time guarantees, mean/median or generation-to-file latency.
P11: Real historical nested agent lineage established in existing Codex rollout session_meta and parent spawn_agent results. Across 1,047 inspected rollouts, 952 had parent_thread_id; 293 two-edge chains had complete files, 13 had explicit root-depth1-depth2 spawn metadata, max observed parent hops = 4. One R0→A1→A2 chain was corroborated at both edges by child's parent IDs and parent spawn output task_name matching child agent_path. No extra test inference-turns/subagents. Correct per-thread ID for this format: payload.id; parent key: payload.parent_thread_id; container payload.session_id may be SHARED across descendants. agent_path and forked_from_id are separate identities/relations, not substitutes for spawn parentage.

DESIGN CONSEQUENCES / DO THIS
One observer and one common event/work graph, NOT separate implementations built around a prematurely presumed App Server limitation. In the current proven VS Code environment, internal owner IPC snapshot+patch follower can supply live activity; persisted rollout metadata supplies verifiable multi-level parentage and recoverable history. Normalize both sources into an event/identity contract, with explicit source/version/capability declarations rather than silently claiming official API stability or universal completeness.
Distinguish root/container session, per-thread agent, parent lineage, agent/task path, fork ancestry and event/item IDs. Include multiple agents per block and multiple blocks per agent. A subscription is observation-only by command allowlisting and cleanup, but private IPC does not itself enforce an immutable read-only capability: the adapter must never send execution/approval commands.
Guard large snapshots and memory/backpressure, track revision gaps and resynchronization. Independent public bug report https://github.com/openai/codex/issues/20781 describes pathological ~116MB snapshots and CPU spikes in a longer VS Code session; not proof this user's extension suffers from it, but a real interoperability risk worth a bounded load check.
Asynchronous agent focus reporting to block(s), if ever needed, should be sparse and not create extra model turns. Preserve user intent: map observes, never directs execution, and no mandatory approval gate.

Unresolved: production durability/continuous traffic, official App Server multi-client access in this stdio deployment, complete live tree under concurrent activity, version-upgrade stability of private IPC, raw hidden reasoning, token overhead under sustained real use, full UI ergonomics. WAYPOINT — DESIGN CONTEXT (DISCOVERY)
Updated: 2026-10-16. Governing discovery record, NOT an approved architecture or implementation roadmap.
Project scope: reusable observability interface for agent-assisted project design and development.

PURPOSE AND USER INTENT
Waypoint is a navigable visual graph of actual project work. It displays where agents and nested orchestrators are working, their available message streams, decisions, checks, requirement/acceptance differences, and evolving plans. It is not an orchestration authority or an approval gate. The map follows real work and may be freely reshaped by authorized working agents. The owner may inspect an initial plan or immediately ask an orchestrator to execute it. No compulsory approval checkpoint is imposed by the viewer.

WHAT COUNTS AS A MAP AND BLOCK
A single shared map can describe a complete project, an epic, one packet, or a particular execution effort. Separate agent-oriented planned views are optional, not the default. Every block represents a self-contained piece of work at any scale, with a formulation of the assignment and conditions of acceptance. Blocks may recursively open into a graph of sub-blocks, to arbitrary practical depth. A block can depend on several predecessors, and may block several successors. These dependencies must remain explicit and independent of on-screen placement.
Horizontal layout is preferred for functional extension or a separately testable tranche; vertical layout is preferred for deeper refinement. These are presentation conventions, not immutable data semantics. A node may be moved or reorganized without changing dependency meaning.
A block may be associated with several agents; one agent may cover several blocks, and working outside the map is legitimate. Waypoint must not force agents to fit its drawing.

BLOCK VISUAL CONTRACT
Left expandable section: assignment, detailed requirements and optionally a link to the source task. Right expandable section: acceptance conditions, actual result, difference between expected and actual, and the agent's assessment where useful. Top: planned/executed test indicators (success, failure, not yet run and potentially invalidated/stale), including fraction passed. Center: directly scrollable original agent messages and work history relevant to the block, optionally links to skills in use; messages can be read by wheel at suitable zoom. Bottom: freely authored status and current activity, with expandable explanatory text, timestamps from events, and blockers where the status merits them. Status is a free-form field rather than an enum or hard enforcement rule. A block marked done may still have failed tests; show both facts without coercing either.
Clicking into a block reveals its nested graph; its block-wide message stream remains available nearby. Messages about transition between blocks may attach to graph edges. Do not litter the canvas with extra free-floating notes. An agent's message stream should not be summarized or duplicated by extra LLM calls just for UI: show provider-exposed messages and traces as available, not inaccessible private chain-of-thought.

VISUAL EXPERIENCE
The default view is the shared roadmap on a wide pannable and zoomable canvas; user can drag the map with the pointer, zoom with the wheel, inspect and collapse nested work, fit to screen and enter fullscreen. Semantic zoom should progressively show topology/status, then block summaries, then scrolling message contents and detailed panels. A minimap and time-travel playback are not current v1 requirements. Preserve plan versions with structural and acceptance diffs.
Active agents appear as compact selectable cards across the top; active orchestrators as compact cards along the left edge. Finished actors fade or move away but remain accessible. Selecting an agent highlights all its work regions; selecting an orchestrator highlights its descendants and their current areas. A subagent who delegates becomes an orchestrator of a deeper level while retaining its original identity and appearing in both sets of cards. Several orchestrators may coexist. Agents are free to take work over a region and to change their plans. Multiple active indicators may appear on one or many blocks.
Activity (live observed progress/heartbeat where genuinely available), self-reported status, test results and source connectivity are different claims. Lack of fresh messages must never imply a process has completed. Prefer an explicit unknown source-health state to a misleading forever-spinning progress indicator. Unexpected statuses can receive subtle attention indicators; ordinary updates should not overwhelm the canvas.

WORKFLOW AND VERSIONING
Plans are a language for discussing what may change in execution, not a fixed contract. Agent-driven changes do not require approval from the viewer. Plans must have old/current versions and human-readable structural diffs. Unchanged nodes keep stable IDs. Local graph changes should be fast; Git stores meaningful checkpoints, not every telemetry event. ChatGPT may prepare batches/archives offline which another executor later applies to the current local baseline; never claim a prepared package has already been integrated.
The owner normally requests changes by chatting to an agent, not by directly editing the canvas. Give blocks stable readable IDs, searchable/navigable references, and links from chat or agent actions. A stored map does not authorize a new Codex run; maintain project resource-policy permission boundaries.

OBSERVABILITY AND DATA DIRECTIONS — PROVISIONAL
Candidate separable logical structures: (1) versioned work/dependency graph; (2) agent parent/child graph; (3) append-only source events and message content; (4) many-to-many agent↔block/edge event references; (5) projected activity/test/status views. Store original messages once; render filtered streams by relationships. Candidate local SQLite event log and fast local CLI/service, with passive read-only Codex rollout adapter first, optional App Server and optional hooks if proven. Git holds plan snapshots. Runtime store and graph are not authority over resulting code: source artifacts and directly observed work are stronger than agent assertion; an agent's assertion is stronger than an outdated map.
ChatGPT should avoid repeated Drive/GitHub writes and can batch map mutations. No extra model inference is justified solely to refresh a status. Local observers must not control or impede Codex, Symphony or the project's other executors. Failure should degrade observability, not stop work.

SCENARIOS EXERCISED CONCEPTUALLY
Initial design and optional owner inspection; agent starts on several branches; subagent becomes another orchestrator; work inside recursively nested block; off-map work; agent replans and removes currently active node; completed block with failed/invalid tests; observer crashes while agents continue; duplicate events/backfill; changes accumulated offline while local machine is unavailable; eventual reconciliation with changed baseline.
Do not turn conceptual scenarios into verified runtime capability.
