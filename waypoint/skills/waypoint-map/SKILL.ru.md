# Подготовка карты Waypoint

Кандидат версии 0.3.1. Не установлен и не зарегистрирован в общей библиотеке. Используй согласованный контекст и `schemas/plan.schema.json` из пакета Waypoint. Скил не запускает работу и не расширяет разрешения.

При создании карты или подключении существующего проекта используй
`.project/passport.json`, если он есть: человеческое название и проверенную
идентичность. Для создания новой идентичности однократно применяй
[общий скил project-passport](https://github.com/ViskyG/agent-skills/blob/main/skills/shared/project-passport/SKILL.md).
Реальный `project_id` из `waypoint.plan/1` сохраняется; если он не равен
паспортному `id`, соответствие записывается в `bindings.waypoint`.
Не выводи названия из Runner ID, не переименовывай старые узлы/задачи и не
считай сам паспорт доказательством поддержки импорта установленным Waypoint.
При обычном обновлении карты повторно загружать общий скил не нужно.

Создавай один граф зависимостей, а не вторую дорожную карту. Каждому содержательному блоку нужны стабильный читаемый ID, имя, задание, критерии приёмки с ID, уместные планируемые проверки и ссылки на исходные материалы. Деление — по осмысленным участкам работы, не по функциям и файлам. Внутри блока может находиться другой граф. Родительство и зависимости заданы явно; горизонтальное расширение и вертикальное углубление — подсказки раскладки. При добавлении работы сохраняй положение существующих блоков. Новое сообщение само по себе не должно перестраивать план.

Для обновления один раз получи актуальную карту и её базовую версию на полезной границе работы. Сохрани ID неизменённой работы; новой дай новые ID. Меняй только нужные требования и зависимости. Передай предлагаемый снимок с base_version и одним request_id; локальный `wp plan-import --merge` объединяет независимые поля. Конфликт — конкретное расхождение для решения, а не разрешение затереть чужие изменения. После неопределённого результата доставки повторяй тот же запрос без изменения содержимого.

Карта следует за работой: не вводи обязательное утверждение, переходы статусов, исключительное владение, тестовые барьеры и запрет делегирования. Задание находится слева, ожидаемый/фактический результат и расхождения — справа. Статус сообщает мнение исполнителя, а не разрешение интерфейса.

Давай исполнителю только `wp --project PROJECT packet NODE` и точные необходимые исходники/контракты. Пояснения должны быть доступны по необходимости, а не перечитываться постоянно. Чат без локального доступа возвращает один ограниченный пакет изменений; он не объявляет, что локальная карта уже обновлена.

## Профиль наблюдаемости 1
Используй контракт `waypoint.observability/1` своего проекта при его поддержке.
Для человеческих вкладок «Задание»/«План» заполняй node.x_observability.intent,
а assignment сохраняй техническим назначением. Умение старого читателя хранить
эти поля не доказывает умение их показывать. Типизированные requires-связи
указывают результат, фазу, область и основание доступности; order не блокирует
работу. Унаследованные условия вычисляются единым resolver, не геометрией UI
и не вторым локальным алгоритмом.

Отбирай алгоритмы на уровне проекта только для существенной собственной логики;
блоки ссылаются на их определения. Укажи реализацию и проверяемость, а реальные
оценки держи в событиях. Миграция от текущей базы сохраняет ID, задания, события
и неизвестные расширения. Недостающее человеческое описание видно как пробел,
а не порождается моделью при просмотре. Отсутствие референса не сокращает запрос
трёх тем. Капсулы чата опциональны; представления проекта/плана не добавляют отчётность.

## Передача по сценариям и идентичность доказательств
Используй [контракт проекта](../../../next-stage/skills/conformance/WAYPOINT_WORKFLOW.md).
Сохраняй один граф, стабильные ID, понятное намерение и отдельное техническое задание.
Свяжи ID приёмки/проверок со сценариями, уместными отрицательными случаями, достаточным
уровнем доказательства и условиями устаревания. Исходники, модульные проверки,
синтетический HTTP/браузер и настоящий нативный источник подтверждают разное.
Запланированная проверка не является фактически пройденной.

Для обязательного входа укажи выход/ревизию, рабочую область и фазу start/finish;
желаемый порядок и вложенность задаются отдельно. Done не доказывает доступность
входа. Передавай неизменяемые/версионные ссылки, не затирай прежние отчёты. Отсутствие
исторического доказательства обозначай неизвестным. Частичное завершение и связанный
ремонт описывай явно; сумма зелёных отметок не делает весь продукт принятым.

Каждому исполнителю и подагенту передай порядок: своя подтверждённая привязка, focus
до работы, действительные исходы критериев до завершения, снятие focus при передаче.
Это точность истории, не исключительное владение, новое утверждение и не команды
управления агентами. Подготовка кандидата, публикация и установка скила различаются.
