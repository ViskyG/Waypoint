# Codex — работать по этой дорожной карте Waypoint

## Разрешённая задача

Когда владелец передаёт этот пакет на исполнение: довести существующий Waypoint в режиме **MIXED** по единому `ROADMAP.plan.json`. Не проектировать всё заново, не создавать вторую реализацию, не переписывать C01–C04. Выбор режима и наличие плана сами по себе не запускают работу; этот файл — инструкция для уже уполномоченного исполнителя.

Пути в карте/пакетах разрешаются **от папки `roadmap/`**. Исходный дизайн/код находятся рядом в `../waypoint/`. В существующем проекте сначала проверить фактическую базу, потом адаптировать пути. Не выполнять слияние распаковкой поверх чужих правок.

## Короткий вход

1. Прочитать `ROADMAP.md` и `packets/WPT-R00.md`.
2. Выполнить R00: целостность, реальная рабочая база, приватное окружение, первый импорт этой карты. Выбрать фактического интегратора. У текущего общего реестра нет подтверждённой регистрации Waypoint; не считать старые handoff-запросы применёнными.
3. После R00 взять **один** пакет C05 либо C06; ознакомиться с его точным reading set. C05 владеет Store/API/миграцией/узким CLI binding seam. C06 владеет web/browser-тестами. Две ветки не редактируют общий Store.
4. C06.3 требует принятого индекса C05.3. C06.1/C06.2 не ждут полного завершения C05.
5. После C05/C06 один интегратор выполняет C07 и возвращает результат по `RETURN_FIELDS.md` плюс шаблон исходного проекта.

При отсутствии результата необязательной Chat/Pro-подготовки Codex может выполнить тот же разрешённый участок сам; не ждать отдельного чата и не дублировать работу живого владельца.

## Проверка и запуск при новой рабочей копии

Из корня распакованного пакета:

```bash
cd waypoint
python3 tools/verify_package.py
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e '.[test]'
cd ../roadmap
python tools/roadmap.py validate
```

Не повторять полный suite после каждого файла. Проверки новой среды и изменённых контрактов выполнить на полезной границе; прежние применимые результаты не обнулять только из-за нового Markdown.

Для первого импорта запустить сервис в одном терминале (проверьте, что каталог/порт не принадлежат другому активному экземпляру):

```bash
cd ../waypoint
python -m waypoint --data "$HOME/.local/share/waypoint-work" serve --port 8769
```

Во втором терминале, из `waypoint/`, с тем же виртуальным окружением:

```bash
. .venv/bin/activate
python -m waypoint --data "$HOME/.local/share/waypoint-work" --project waypoint plan-import ../roadmap/INITIAL_IMPORT.json
python -m waypoint --data "$HOME/.local/share/waypoint-work" --project waypoint emit ../roadmap/INITIAL_SOURCE_EVIDENCE.json
python -m waypoint --data "$HOME/.local/share/waypoint-work" --project waypoint packet WPT-C05
```

`INITIAL_IMPORT.json` имеет `base_version:null` и предназначен **только для нового project head**. Если карта уже есть, получить актуальный экспорт, сопоставить изменения и использовать настоящий base_version. Ошибка base_conflict не разрешает сбрасывать БД. `INITIAL_SOURCE_EVIDENCE.json` содержит только исторические исходные результаты C01–C04; не импортировать его как обновление текущих рабочих статусов.

Команда `url` печатает локальную ссылку с read capability. Открывать её можно локально, но нельзя помещать в отчёт, публичный лог или скриншот.

## Как получать и менять карту дальше

Когда сервис работает, `wp --project waypoint packet WPT-C05` возвращает назначение/приёмку/тесты/ссылки/детей. Укажите тот же `--data`, если он не задан через `WP_DATA`. Если сервис недоступен, тот же пакет доступен в `packets/WPT-C05.md`; это generated view, а не второй план.

После выполнения/перестройки плана получить актуальную версию:

```bash
python -m waypoint --data "$HOME/.local/share/waypoint-work" --project waypoint plan-export ../roadmap/working-export.json
```

Export откажется молча затереть существующий файл. Внесите нужные изменения в `working-export.json` с сохранённым base_version, добавьте один новый request_id для этого изменения, затем:

```bash
python -m waypoint --data "$HOME/.local/share/waypoint-work" --project waypoint plan-import ../roadmap/working-export.json --merge
```

При неизвестном результате доставки повторять то же тело с тем же request_id; после конфликта сначала новый read/resolve, не слепой повтор. Не подменять текущий экспорт первоначальным ROADMAP.plan.json.

## Сигналы и экономия

После C05.1 использовать **проверенный отдельный native ID исполнителя**, а не общий session_id. `focus` отправлять при смене области, `status` — при существенном изменении, `test` — по факту проверки, `done --result --diff` — по фактическому результату. Тексты диалогов поступают от источника, не пересказываются для карты. Не угадывать идентичность: до подтверждения оставлять сообщения без назначения. Файл с literal `NATIVE_THREAD_ID` — только обозначение места под проверенное значение, не допустимый реальный ID.

Не запускать inference-turns/субагентов ради статистики. Работать с естественными событиями, а реально необходимый отдельный опыт согласовать в узком объёме. Не изменять чужие клиенты, hooks/auth, глобальные скилы, лицензии и расписания как побочный эффект.

## Граница публикации

Не применяйте JSON из `handoff/` как замену реестра. Это запрос координации, не команда исполнения. Текущие registry/inbox прочитаны при планировании, не изменены. Для записи требуется актуальное полное содержимое и реальная защита от конкурентного изменения. Работа по локально переданному пакету возможна без нового планировщика.
