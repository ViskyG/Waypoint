# Контракт достоверной работы с картой Waypoint

Этот контракт связывает проектировщика дорожной карты, исполнителя Codex и аудитора. Он уточняет запись уже разрешённой работы. Waypoint остаётся наблюдателем: статусы не управляют исполнителем, focus не резервирует участок, проверки не становятся новым программным барьером. Глобальные кандидаты в этом каталоге не опубликованы и не установлены. Проектные скилы остаются черновиками `draft-candidate` версии 0.3.0.

## Проектировщик дорожной карты

Используй один согласованный граф. Сохраняй ID, исходные задания, историю, неизвестные расширения и координаты неизменённых узлов. Человеческое намерение `x_observability.intent` отдельно от технического `assignment`; статусы присоединяются из событий, а не из второй сводки.

Для содержательного пакета задай ожидаемое наблюдаемое изменение, стабильные ID критериев/проверок, точные входы, область изменений, достаточное доказательство и условия его устаревания. Свяжи критерий с пользовательским сценарием. Добавляй подходящие отрицательные случаи: отсутствующий/устаревший вход, пустой поток, ошибка, запоздалый ответ/свидетельство, смена проекта, восстановление, несовместимая ревизия. Не требуй каждый случай для любой простой задачи.

Разделяй уровни доказательств:

| Уровень | Что подтверждает | Чего недостаточно утверждать |
|---|---|---|
| Чтение исходников | Конкретное правило или отсутствие опасного пути | Выполнение интеграционного сценария |
| Модульная/контрактная проверка | Проверенный алгоритм и границы на указанных данных | Настоящий браузер или текущий Codex |
| Mocked UI / set_content | Интерфейс на контролируемом ответе | Браузер→HTTP→Store |
| Синтетический браузер→HTTP→Store | Настоящий транспорт и продукт на явно искусственных данных | Настоящий источник Codex |
| Действующий сервис / настоящая база | Установка, миграция, восстановление в указанном объёме | Все пользовательские сценарии |
| Настоящий Codex→Store→браузер | Точное проверенное наблюдение текущего источника | Любые будущие форматы, все агенты и универсальная задержка |

`requires` описывает конкретный выход и его ревизию, потребителя/область, start/finish и рабочую копию. `order` — желаемый порядок; вложенность — отдельное отношение. Done не подтверждает доступность. Используй общий resolver и фактические capabilities сервиса; наличие поля в старом viewer не доказывает поддержку функции. Значимую пользовательскую логику включай в единый каталог алгоритмов с точными ссылками на реализацию и тестируемость; выполненные тесты/измерения остаются событиями.

Доказательство хранится по неизменяемому или версионному пути с хешем применимой ревизии. Следующая проверка получает новый путь. Не затирай исторический результат новой проверкой под прежним именем. Укажи допустимое повторное использование и что его отменяет: изменение кода, входов, среды, конфигурации либо контракта по существу. Планируемый тест не является пройденным.

Передача исполнителю содержит собственную привязку каждого агента, focus до работы, регистрацию действительных результатов по ID до объявления завершения и снятие focus при передаче. Капсулы чата остаются необязательным способом поставки; выбранные ресурсные разрешения сохраняются.

## Исполнитель: точные существующие команды

Ниже шаблоны, не команды для запуска с буквальными заглушками. Подставь реальный проект, существующие NODE/TEST_ID, свою проверенную rollout-запись и новые приватные пути. Все глобальные аргументы CLI стоят перед подкомандой. Не публикуй read/write capability, переписки, binding или базу в доказательствах.

Один раз создай отдельную привязку именно этого исполнителя. `bind` проверяет `CODEX_THREAD_ID` и первую мета-запись своего rollout; файл назначения должен быть новым. Не меняй переменную окружения ради прохождения проверки и не копируй binding родителя. Каждый подагент выполняет собственную привязку.

```bash
wp --project PROJECT bind --rollout OWN_ROLLOUT --output NEW_OWN_BINDING
wp --project PROJECT --binding OWN_BINDING packet NODE
wp --project PROJECT --binding OWN_BINDING focus NODE
wp --project PROJECT --binding OWN_BINDING status NODE "В работе" --why "Конкретный текущий участок"
```

Если привязка недоступна, не придумывай ID и не приписывай работу родителю. Сообщения остаются непривязанными; один раз устрани конкретный недостаток интеграции и продолжай независимую разрешённую работу. Focus описывает будущие наблюдения с фактической границы источника; не переносит прежний поток к новому блоку. Пустой чат сам по себе не доказывает выполнение или провал.

Запускай только необходимые проверки и сохраняй фактические результаты. Для каждого затронутого существующего ID зарегистрируй исход и run ID; повторно использованное доказательство сохраняет реальное основание прежнего запуска.

```bash
wp --project PROJECT --binding OWN_BINDING test NODE TEST_ID passed --run ACTUAL_RUN_ID --basis "immutable/proof-RUN.json; actual level; code/input/environment basis"
wp --project PROJECT --binding OWN_BINDING test NODE OTHER_TEST_ID not_run --run ACTUAL_RUN_ID --basis "Не выполнялась: конкретная причина; оставшееся обязательство"
```

Допустимы `passed`, `failed`, `skipped`, `error`, `not_run`. `--current` — ручная оценка исполнителя: CLI не проверяет хеши кода автоматически. Отсутствие `--current` оставляет freshness неизвестной. Не отмечай новое выполнение, если только повторно регистрируешь старое доказательство. Не запускай проверку ради заполнения индикатора и не суммируй пересекающиеся наборы как процент готовности продукта.

Для структурированных оснований и явной поздней регистрации используй существующий `emit` с подготовленным JSON. Пример структуры одного события:

```json
{
  "events": [{
    "schema": "waypoint.event/1",
    "event_id": "NEW_UNIQUE_EVENT_ID",
    "project_id": "PROJECT",
    "agent_id": "codex/VERIFIED_OWN_ID",
    "source": "evidence-registration",
    "kind": "test.result",
    "at": "ACTUAL_REGISTRATION_TIME_ISO8601",
    "node_ids": ["NODE"],
    "edge_ids": [],
    "payload": {
      "test_id": "TEST_ID",
      "run_id": "ACTUAL_RUN_ID",
      "outcome": "passed",
      "freshness": "unknown",
      "plan_version": "ACTUAL_CAPTURE_VERSION",
      "evidence_levels": ["actual_local_service"],
      "evidence_refs": ["immutable/proof-RUN.json"],
      "basis": "Точный сценарий, прежний запуск, ревизия и среда",
      "registered_from_existing_evidence": true,
      "registration_method": "Поздняя регистрация существующего доказательства; новое выполнение не заявлено"
    }
  }]
}
```

`at` — действительное время регистрации; время прежнего выполнения указывай в основании, только если оно сохранено. Перед отправкой замени заглушки и проверь фактическое содержание артефакта. `emit` валидирует форму, но не выполняет тест и не доказывает истинность файла.

```bash
wp --project PROJECT --binding OWN_BINDING emit PREPARED_EVENTS_JSON
```

Для подтверждения доступности выхода подготовь через тот же `emit` отдельный `dependency.observation`, только если сервис поддерживает контракт. В payload нужны точные `edge_id`, `consumer_id`, `requirement_fingerprint` текущего packet, действительный `workspace_ref`, `availability` (`available`, `missing`, `waived`), `basis` с `kind/ref/revision` и объяснением, `occurred_at`. Ревизия — хеш неизменяемого артефакта или другая точная поддержанная ссылка, не вывод из статуса done. `waived` требует действительного объяснённого основания в разрешённом объёме, а не удобства обхода. После изменения артефакта сохрани старое свидетельство и добавь новое. Сервис не читает произвольный файл и не перепроверяет автоматически его текущие байты.

Перед завершением сопоставь ожидаемое/фактическое поведение и обязательные критерии с имеющимися основаниями. Честно запиши незапущенное, провал и остаток; частичная поставка не становится полной приёмкой. Если done описывает выполненную часть при явном исключении, сохрани исключение и связанную оставшуюся работу; наблюдатель не запрещает статус программно.

```bash
wp --project PROJECT --binding OWN_BINDING done NODE --result "Фактически выполнено; доказательства; границы" --diff "Оставшийся недостаток или отсутствие расхождений в проверенном объёме"
wp --project PROJECT --binding OWN_BINDING focus
```

`done` не снимает focus. При переходе к следующему пакету вместо пустого focus можно явно объявить новую область. Не оставляй последующий аудит в завершённом блоке. Не делай guessed relink старых записей: коррекция возможна только по явной доказанной идентичности/привязке, сохраняя исходную историю. Не отправляй synthetic notes ради наполнения пустых чатов. Сообщения и инструменты наблюдаются автоматически; heartbeat, дополнительный модельный опрос и команды управления агентами не нужны.

`QUEUED_LOCALLY` означает сохранение в outbox, не доставку сервису. Сохрани недоставленный сигнал один раз, не запускай inference-цикл повторов. Ошибку версии/конфликта импорта нельзя выдавать за применение плана. Разрешённая полезная работа продолжается при сбое телеметрии.

## Изменение карты с сохранением истории

```bash
wp --project PROJECT plan-export NEW_EXPORT_JSON
wp --project PROJECT plan-import PREPARED_PLAN_JSON --base CAPTURED_BASE_VERSION --merge --request-id STABLE_REQUEST_ID
```

Экспорт создаёт новый файл и содержит `base_version` и `plan`. Подготовь отдельный предлагаемый файл из свежего экспорта, сохранив неизвестные расширения и ID. Стабильный request ID повторяется только с идентичным содержимым после неопределённой доставки. Конфликт требует разбора конкретного различия; не повторяй изменённый payload под прежним ID и не затирай чужую работу. Фактический receipt/версия подтверждают применение; локальный JSON или чат без доступа не означают изменение действующего Waypoint.

## Аудитор и ремонт

Проверяй на запрошенной границе фиксированную версию карты, критерии, статусы, декларации областей, реальные исходы сценариев и пригодность доказательств. Различай исторический факт, текущую декларацию и нынешнюю проверку байтов. Позднее свидетельство не доказывает, что физического входа раньше не существовало. Текущее satisfied не восстанавливает отсутствующую историю; серия предупреждений одного интервала не равна серии независимых инцидентов.

Для вывода нужны ожидание, факт, уровень доказательства, точная версия/seq/артефакт, причина либо неопределённость, следствие, минимальный ремонт и адресное подтверждение. 47 зелёных отметок не означают прохождение всего продукта. Отделяй прежние неудачи, поздние исправления, synthetic воспроизведение и живую интеграцию. Сохраняй действительные незатронутые результаты, исходные события и ID.

Доказанный обязательный недостаток, существенно противоречащее завершению свидетельство, заявленная незапущенная проверка или недоступный необходимый текущий артефакт требуют явного пересмотра завершения либо связанного `-FIX`/`-FIX-2` с исходной проблемой и условиями закрытия. Недостаток доказательств — `unverified`, не вымышленный провал; улучшение вне принятого объёма остаётся предложением. Никаких новых барьеров разрешений, автоматического управления агентами и обязательного полного перегона тестов это не вводит.

Код, целевые проверки, фактическая интеграция, Git-публикация, установка проекта и публикация/установка глобальных скилов сообщаются раздельно. Новое поведение подтверждается адресно на подходящем уровне; неизменённые доказательства используются повторно.
