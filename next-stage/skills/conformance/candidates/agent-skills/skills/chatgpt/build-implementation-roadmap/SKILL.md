# Execution Roadmap
Navigation: project-workflow. Inputs: Design Context, completed design-session handoff, current global capsule registry, actual project/artifact/evidence state and execution policy. Required: workflow-state-and-transit P1, P5, P7-P8; evidence-driven-validation. Next: orchestrate-roadmap-across-executors.


This stage plans execution; it does not rebuild the architecture or maintain runtime status. Prefer a dedicated Pro planning pass, but another permitted chat can do it. It is a separate responsibility even if a tiny project's remaining plan is one compact integration instruction.


## One graph, two usable execution forms
Build a dependency graph optimized first for useful Codex progress per unit of reading/reasoning/testing. Expose only a small local frontier (current packet and a few safe next options) to an executor, not the full graph for every step.


Derive Runner waves from the SAME graph: group coherent packets that can be prepared from stable inputs without intermediate target evidence. Each wave has identifiable contracts, an integration boundary and diagnostic checks. Do not maintain two independently changing roadmaps. Do not flatten real dependencies merely to make a large wave, or design a high-latency chat route requiring dozens of microscopic edit-test round trips.


## Optional capsule supply
Do not wait for capsule implementation before constructing the roadmap. A capsule is an optional supply route for required behavior, not an unavoidable wait on a particular chat.
- Result already exists: schedule only needed adaptation/integration/evidence, not duplicate implementation.
- Chat is working: plan independent work now and a later integration point. Udot tells Codex about incoming work before it starts duplicating that scope.
- No result yet, failed delivery or user Pro delayed: include an alternate implementation route allowed by resource policy. Reuse any recoverable artifacts and stable contracts.
- All required code already written by Pro: no fictitious capsule work; plan the genuinely remaining integration/verification only.


Ask for Pro help in advance through Udot, since the user may not start it promptly. Include the Codex-Pro/manual-chat alternative when permitted. At a real blocking frontier, report the exact need and continue independent work; do not promise impossible continuous progress or manufacture tasks to conceal a hard dependency.


## Packet contract
For each meaningful packet provide purpose/expected result, starting-state assumptions, hard dependencies and shared contracts, exact reading set, owned files/logical anchors, work/output, sufficient evidence, safe next/alternate work and escalation condition. Add eligible/preferred executor and handoff input where useful. Eligibility is not a claim and cannot expand budget permission.


Prefer context reuse, early stable shared interfaces, coherent user-visible progress and early tests of risky dependencies. Explain non-obvious ordering briefly. Size work by meaningful behavior, not line counts. Do not make every class a packet.


Parallel lanes need non-conflicting physical/logical change ownership as well as conceptual independence. Prefer separate files or stable anchors. For unavoidable overlap specify the integration owner/order and what Udot must tell Codex. A task waiting on a long test/build should have another safe task available when one genuinely exists.


## Reading and verification economy
Specify "read A and section B to do X", not "study the project first". Preserve exact source needed for safe replacement; omit full architecture/history and optional rationale until needed. A compact derived task-context note is worthwhile only if it demonstrably reduces repeated reading.


Plan what each check establishes and what invalidates previous evidence. Use direct observable operation when it suffices for the relevant claim; do not add a duplicate test solely because a test could exist. Integration/broad checks belong at meaningful dependency, capability or release boundaries, with earlier checks for genuinely risky interfaces. No obligatory full test/audit cycle after every task and no giant undiagnosable untested batch.


Keep evidence state inside the existing runtime record unless a separate EVIDENCE_STATE actually saves effort. Reuse current applicable evidence; unchanged source does not make evidence reusable after relevant environment/configuration changes.


## Route policy and return of the machine
ECONOMICAL never falls back to Codex because it is faster/easier. Separate technologically indispensable infrastructure operations from development and bound the exception. MIXED/CODEX_ENABLED may use chats and Runner to prepare ahead, but an optional slow chat must not stop otherwise useful permitted Codex progress.


When the machine is offline, plan independent preparation and pending-artifact storage, not application of untested layers to a supposedly current baseline. On return, synchronization of local/integrated Drive/GitHub precedes application/test/development. Reference the existing Runner protocol, not a guessed new command schema.


## Deliverable
Give a navigable roadmap, bounded execution packets or sections, graph dependencies, Runner grouping, minimal reading paths, evidence/invalidation plan, user/Pro escalation points and initial runtime frontier derived from observed state. Existing STATE.md is allowed; avoid many small mirrored mutable files. Udot maintains actual assignment, receipts and reorderings later.


Explain the next actual user/system step and chosen budget policy. The roadmap is complete enough when an executor can progress without reopening material design questions; unresolved central design gaps are explicit, not hidden behind a fabricated runnable plan.



## Human-readable plans and evidenced dependencies
For each meaningful node, author its project context, intended change and observable
outcome separately from the executor assignment. The owner's Plan outline and Task
view use the same intent; join status from existing node events, never ask an agent
to maintain a second status summary. Preserve legacy technical assignments.

A hard edge names a required producer output, affected consumer scope, start/finish
phase and evidence of availability. Keep preferred coding order and containment
separate. Check inherited dependencies using the SAME resolver in packet/frontier
and UI projections; collapsed links disclose their actual endpoints. Do not infer
input availability from free status text alone. The observer preserves early work
and unknown evidence instead of enforcing an execution gate.

Use the project's compatible machine-readable profile as the common authoring
source, preserving IDs, version guards and unknown extensions. Add algorithm
references only for substantial custom logic needing correctness/cost review;
framework names and trivial wrappers are not inventory entries. Runtime algorithm
checks/measurements remain evidence, not repeated plan editing.

Chat capsules remain OPTIONAL supply for a node's result. Every roadmap retains a
permitted non-chat route; absence of chat delivery is not a hard dependency. Existing
claims and integration ownership still prevent duplicate work. These additions do
not change the selected resource policy, create schedules or authorize installation.

## Scenario evidence and completion meaning
For every meaningful packet map acceptance IDs to concrete user scenarios and the
least costly evidence that establishes each claim. Distinguish source inspection,
unit/contract checks, synthetic browser-to-HTTP integration, actual installed service
and actual native-source integration. Include relevant negative cases: unavailable
or stale input, failure, empty history, late receipt, reconnect and incompatible
revision where applicable; do not demand every case for unrelated simple work.

Specify output identity/revision, applicable workspace and start/finish phase for a
real required input; preferred order stays an order edge. Plan availability evidence
separately from done status. Stable immutable evidence references must survive later
validation rather than being overwritten under the same historical filename. State
what invalidates reused evidence and what remains unverified. Do not create fake
execution history, authored passing tests or runtime summaries in the plan.

The handoff must tell each permitted executor to use its own binding, declare scope
before work, record actual checks by criterion ID before completion, and release scope
at handoff. Use one graph, readable intent and a separate technical assignment. A
completed count alone cannot claim all scenarios or an entire product passed. Keep
real unresolved work explicit; fix packets link the original issue and preserve valid
unaffected work. This adds no approval gate, mandatory repeated audit or agent control.
